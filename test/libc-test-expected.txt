# One or more profile rules per corpus test:
#
#     <name>  <profile selector>  <disposition>  <reason>
#
# The dispositions are PASS, BUG, UNIMPL, NA and FLAKY.  Every non-PASS
# row requires a reason.  Compiler/process observations remain separate:
# pedantic requires BUG to build and fail and UNIMPL not to build; strict
# performs those probes and then rejects either disposition.
#
# A disposition may be overridden by adding a more specific profile rule.
# Profile dimensions include runtime, target and host architecture, WOW64,
# kernel32 support and named runtime capabilities. The shared resolver
# rejects ambiguous matches and profiles for which no rule exists. This
# baseline deliberately claims only the configuration in which it was measured;
# another platform must be annotated before it can use the ledger.
#
# This file does NOT need one row per real case. It lists only the cases
# whose disposition deviates from PASS, plus one trailing wildcard row
# (case "*") that declares PASS as this corpus's own default for every
# case with no more specific row. That row is not decoration:
# tools/testlib.py's resolve() falls back to a case="*" rule whenever a
# case-specific search comes up empty, so "everything else is PASS" is a
# real, matched rule here, not a hidden default in Python or in
# tools/libc-test.sh. Which cases are "real" -- so that a case with no row
# here still gets adjudicated, rather than silently dropped -- comes
# independently from tools/libc-test.sh's own glob over
# third_party/libc-test/src/{functional,regression}/*.c (see its
# read_ledger()), not from what happens to be listed below. This mirrors
# test/posix-opts-expected.txt's own wildcard row exactly (see commit
# 93bbaa3, "test: default posix-opts cases to PASS via an explicit
# wildcard row"); this ledger previously took the opposite position --
# every real case needed an explicit row, and an absent one was a hard
# error -- until the project decided that PASS-by-default is fine here
# too, as long as the default is a real, visible row rather than a
# hidden one.
#
# Baseline: ntlibc 661c577, libc-test 68edb8b, x86_64-win32-tcc, under
# the project's patched Wine (which implements RtlCloneUserProcess, so
# nothing here is Wine-fork-blocked; on stock Wine several of these
# become NA at run time instead, by design).
#

# 2026-09-01 correction (crypt, daemon-failure): the "2026-09-01 refresh"
# paragraph above says crypt's UNIMPL reason "was checked and is still
# accurate" and daemon-failure's UNIMPL reason was merely reworded to
# "daemon() is deliberately unimplemented" -- both claims are wrong as of
# this correction. include/crypt.h and src/unistd/crypt.c are real,
# implemented files (a from-scratch traditional DES crypt(3), per that
# file's own header), and src/unistd/daemon.c is a real fork()+setsid()+
# chdir()+open()+dup2() implementation, declared at include/unistd.h
# with no "undefined-ok" marker. Rebuilt both against the current tree
# with x86_64-win32-tcc: both now compile AND link clean (no more
# "crypt.h not found" / "unresolved reference to 'daemon'"), so UNIMPL
# -- which requires the build itself to fail -- can no longer stand for
# either row; not run under Wine in this environment (none installed).
# Since neither crypt.c nor daemon.c has an nt/ or linux/ split (crypt()
# is pure portable ISO C; daemon() is a thin, platform-generic wrapper
# over fork()/setsid()/chdir()/open()/dup2(), each already exercised
# elsewhere on both backends), the unmodified upstream corpus source for
# each was also built and run natively against this project's aarch64-
# linux backend as supporting evidence of runtime behaviour, not just a
# link probe:
#   * crypt: builds and runs to completion (rc=1), but every one of its
#     cases exercises a glibc/BSD *extension* hash format ("$1$" MD5,
#     "$2a$"/"$2x$"/"$2y$" bcrypt, "$5$" SHA-256, "$6$" SHA-512) --
#     ntlibc's crypt() deliberately implements only traditional
#     2-character-salt DES, the POSIX-mandatory minimum (src/unistd/
#     crypt.c's own header), and correctly returns NULL/EINVAL for a
#     salt starting with '$' (not in the DES salt alphabet), the same
#     failure mode a real crypt() gives for a hash algorithm it was not
#     built with. All 30 t_error() calls in the run are exactly that
#     rejection, case by case -- a design difference from a corpus test
#     that assumes glibc's multi-algorithm crypt(), not a defect in the
#     POSIX-mandatory DES path this library implements.
#   * daemon-failure: needs upstream t_fdfill() to exhaust the fd table
#     so daemon()'s internal open("/dev/null") fails with EMFILE: the
#     one case this test exists to check. test/libc-test-shim-src/
#     libc-test-shim.c's own t_fdfill() is a stub (no enforced
#     RLIMIT_NOFILE on this target), so that premise is never
#     established; the native run prints the shim's SHIM-STUBBED marker
#     and daemon() genuinely succeeds and detaches (ppid becomes 1)
#     instead of failing, exactly as follows once fd exhaustion does not
#     happen. tools/libc-test.sh's own SHIM_MARK detection turns any run
#     whose log contains that marker into rc=77/NA, never a pass or
#     fail -- the same treatment pthread_atfork-errno-clobber/
#     malloc-oom/setenv-oom/pthread_create-oom already get above for the
#     same stubbed-helper reason.
# Both rows move UNIMPL -> NA below (not PASS): each corpus test still
